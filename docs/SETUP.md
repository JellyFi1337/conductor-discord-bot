# Настройка Conductor: оба бота и серверы

Основной и тестовый Conductor — **два разных приложения Discord**. У каждого свой токен, свой список серверов и свой процесс. Из одного `.env` поднимается только выбранный режим (`BOT_MODE`). Чтобы держать обоих онлайн сразу, нужен второй контейнер со своим файлом `.env.test`.

Пока ранги никому не выданы, команды владельца делает владелец приложения Discord (и id из `OWNER_USER_IDS`). Галка Discord «Администратор» открывает команды бота **только пока ранг Специального никому не привязан** — временный вход свежего сервера. После привязки Специального она даёт лишь обход лимитов. Всё, что настраивается после каркаса, живёт в `/admin panel`.

Как поднять процесс: Windows — [DEPLOY.md](DEPLOY.md), пустой Ubuntu 24.04 — [deploy/ubuntu-24.04/README.md](../deploy/ubuntu-24.04/README.md). Тот же порядок внутри Discord — `/help` → «Первые шаги».

## 1. Что должно получиться

| | Основной бот | Тестовый бот |
| --- | --- | --- |
| Приложение в портале | своё, имя любое (например Conductor) | другое (например Conductor Test) |
| Токен | `DISCORD_TOKEN` в одном `.env` | `TEST_DISCORD_TOKEN` в том же `.env` |
| Серверы | только `GUILD_IDS` / `PUBLIC_GUILD_ID` | только `TEST_GUILD_IDS` / `TEST_GUILD_ID` |
| `BOT_MODE` | `live` | `test` или `beta` |
| Public Bot | выкл | выкл |
| Чужой сервер | выходит сам | выходит сам |

Не приглашайте тестового на общедоступный сервер и основного на тестовый. Если id нет в списке **этого** процесса, бот выйдет при старте или сразу после входа.

## 2. Что нужно до портала

- Аккаунт Discord, которым вы владеете приложениями (или роль Admin/Developer в Team приложения).
- Право **Управлять сервером** на обоих серверах — иначе Discord не даст добавить бота.
- Docker Desktop (Windows) или пакет [deploy/ubuntu-24.04](../deploy/ubuntu-24.04/README.md) на пустом Ubuntu 24.04. Локальный Python без Docker годится только для разработки (SQLite).
- Два сервера: общедоступный и отдельный тестовый. Тестовый можно создать пустым специально для Conductor.

Владелец приложения — тот, кто нажимает New Application. Именно он (и Team admin/developer) обходит ранги бота. Дополнительных людей можно вписать в `OWNER_USER_IDS`.

---

## 3. Два сервера Discord

### Общедоступный

Обычный сервер сообщества. Сюда приглашается **только основной** бот.

### Тестовый

Отдельный сервер. Сюда приглашается **только тестовый** бот. На нём же отрабатывают `/owner seed` и `/diagnose`.

Рекомендации для тестового сервера:

- Название вроде «Conductor DEV», чтобы не перепутать.
- Вы — владелец сервера.
- Каталожных ботов (DSMonitoring, Server Monitoring) не добавляйте.
- Community / Server Discovery не включайте.

Оба сервера могут быть в одной учётной записи. Это два разных id.

## 4. Режим разработчика и id

В клиенте Discord:

1. **Настройки пользователя → Дополнительно → Режим разработчика** — вкл.
2. ПКМ по значку **сервера** → **Копировать ID сервера**. Это число из ~17–19 цифр.
3. ПКМ по своему аватару → **Копировать ID пользователя** — если нужны дополнительные разработчики в `OWNER_USER_IDS`.

Запишите:

| Что | Куда потом |
| --- | --- |
| Id общедоступного сервера | `GUILD_IDS` или `PUBLIC_GUILD_ID` |
| Id тестового сервера | `TEST_GUILD_IDS` или `TEST_GUILD_ID` |
| Id вашего пользователя | `OWNER_USER_IDS` (необязательно, если вы владелец приложения) |

Application ID (Client ID) бота копируется в портале, не с сервера.

## 5. Два приложения в Developer Portal

Сделайте шаги этого раздела **дважды**: сначала основное приложение, потом тестовое. Настройки портала у них одинаковые, различаются только имя и токен.

Откройте [Discord Developer Portal](https://discord.com/developers/applications) и войдите тем аккаунтом, который будет владельцем бота.

### 5.1. Создать приложение

1. **New Application**.
2. Имя: `Conductor` или `Conductor Test`.
3. Примите условия, **Create**.

На странице **General Information**:

- Запомните **Application ID** — он же Client ID для ссылки-приглашения.
- Иконку и описание можно поставить позже, на работу бота не влияют.

Если приложение в **Team**: команды `/owner` доступны членам с ролью Admin или Developer. Остальным — только через `OWNER_USER_IDS`.

### 5.2. Installation (новый вид портала)

Если слева есть пункт **Installation**:

1. **Installation Contexts**
   - **Guild Install** — вкл.
   - **User Install** — выкл. Conductor не ставится «к пользователю».
2. **Default Install Settings** (Guild Install):
   - Scopes: `bot`, `applications.commands`.
   - Permissions: список из §6 ниже. **Administrator не ставьте.**
3. Ссылку Default Install можно не использовать: надёжнее собрать URL в OAuth2 (§6).

### 5.3. Вкладка Bot

1. **Reset Token** → Copy. Оба токена кладите в один `.env`:
   - основной → `DISCORD_TOKEN`;
   - тестовый → `TEST_DISCORD_TOKEN`.
   Какой из них возьмёт процесс, решает `BOT_MODE`. Во втором файле `.env.test` можно оставить только `DISCORD_TOKEN` тестового приложения.
   Токен показывается один раз. Утечка = сброс и перезапуск процесса.
2. **Public Bot** — **выкл**. Иначе любой сможет добавить бота на свой сервер. С чужого он всё равно выйдет, но заявки и логи шума не нужны.
3. **Requires OAuth2 Code Grant** — выкл.
4. **Privileged Gateway Intents** — включите ровно эти два:
   - **SERVER MEMBERS INTENT** — состав, перепись, досье, роли, верификация.
   - **MESSAGE CONTENT INTENT** — текст сообщений: автомод, логи правок, история, лестница.
5. **PRESENCE INTENT** — выкл. Онлайн во вкладке `/diagnose` → Сейчас без него не рисуется; голос считается и так.
6. Интент личных сообщений (анонимные тикеты) бот включает **в коде** (`intents.dm_messages`). Отдельной галки в портале нет.

Бот в коде также включает: guilds, moderation, voice_states, guild_messages, guild_reactions, invites, auto_moderation. Это не привилегированные интенты, в портале их включать не нужно.

### 5.4. OAuth2

На **OAuth2 → General**:

- **Client ID** совпадает с Application ID.
- Redirects не нужны: входящего HTTP у бота нет.

Дальше — генератор ссылки в §6.

### 5.5. Чего в портале делать не нужно

- Не включайте Public Bot «на потом».
- Не требуйте OAuth2 Code Grant.
- Не добавляйте бота через «Add to Server» из магазина приложений.
- Не выдавайте в инвайте право Administrator: команды от этого не откроются, а иерархия ролей станет опаснее.

## 6. Приглашение на сервер

Каждого бота приглашайте **только на свой сервер**. Ссылку собирайте заново для каждого Application ID.

### 6.1. Кто может пригласить

В клиенте Discord у вас на целевом сервере должно быть право **Управлять сервером** (Manage Server). Обычно это владелец сервера.

### 6.2. Генератор в портале

**OAuth2 → URL Generator**:

1. Scopes:
   - `bot`
   - `applications.commands` — без него слэш-команды не появятся.
2. Bot Permissions — отметьте **обязательные** (их же проверяет `/diagnose`):

| Право в портале | Зачем |
| --- | --- |
| Manage Roles | роли каркаса и брокер |
| Manage Channels | категории, каналы, комнаты, тикеты |
| Ban Members | бан и ловушка верификации |
| Kick Members | кик |
| Moderate Members | тайм-аут |
| Move Members | хаб голосовых комнат |
| Manage Messages | чистка, закреп панелей, ночная уборка логов |
| View Audit Log | санкции мимо бота, лояльность |
| Create Instant Invite | рекрут-ссылки `/recruit` |

3. Дополнительно отметьте, иначе карточки и голос не заработают, хотя `/diagnose` эти строки может не подсветить:

| Право | Зачем |
| --- | --- |
| View Channels | видеть каналы |
| Send Messages | ответы и панели |
| Embed Links | карточки |
| Attach Files | доказательства, транскрипты |
| Read Message History | история, уборка своих сообщений |
| Add Reactions | реакции на панелях, где они есть |
| Use External Emojis | значки приложения |
| Connect | зайти в голосовой канал |
| Speak | хаб комнат |

4. **Administrator не отмечайте.**
5. Скопируйте сгенерированный URL.

Готовая ссылка (подставьте Application ID своего приложения):

```
https://discord.com/oauth2/authorize?client_id=APPLICATION_ID&permissions=1099800374487&scope=bot%20applications.commands
```

Число прав — обязательные из кода плюс дополнительные из таблицы выше. Если портал покажет другой набор галок при той же ссылке, сверьте вручную.

### 6.3. Выбор сервера

1. Откройте ссылку, будучи залогинены в Discord.
2. В списке выберите **только** сервер этого бота:
   - основное приложение → общедоступный;
   - тестовое → тестовый.
3. Подтвердите права, **Авторизовать**.
4. Если Discord просит капчу — пройдите, это нормально.

После этого бот висит на сервере серым (оффлайн), пока не запущен процесс. Это ожидаемо.

Не приглашайте того же бота на второй сервер «на всякий случай»: при старте он оттуда выйдет.

## 7. Настройки сервера после приглашения

Повторите на **обоих** серверах. Раздел настроек: значок сервера → **Настройки сервера**.

### 7.1. Роль бота — выше каркаса

**Роли** → найдите роль с именем приложения (Conductor / Conductor Test).

Перетащите её **выше** всех ролей каркаса, которые бот будет менять: ранги следящих, Old, лестница, репутация, достижения, подписки, «Верифицирован», мут.

Если роль бота ниже управляемой роли, Discord запретит выдачу и снятие. `/owner seed` тогда покажет список, но не подключит («не хватает места под ролью бота»). `/diagnose` → Настройка покажет позицию.

Права роли после инвайта должны совпадать с таблицами в §6. Если чего-то нет — включите на роли бота вручную. Не ставьте Administrator.

### 7.2. Каркас собирает бот

`/admin` → **Каркас** → **Собрать сервер** создаёт недостающие категории, каналы и роли. Свои каналы сопоставьте до сборки — бот запоминает id и не переименовывает. Повторная сборка на уже работающем сервере ничего не ломает и не плодит дубли. Discord может закрыть создание после пачки create/delete: не удаляйте объекты пачками. Свои чаты общения — после сборки, внутри категории «Сервер».

### 7.3. Безопасность и модерация Discord

| Настройка | Рекомендация |
| --- | --- |
| Уровень проверки | любой; верификацию людей делает Conductor |
| Фильтр непристойного содержимого | на ваше усмотрение |
| 2FA для модераторов | можно вкл; на бота не действует |
| Нативный AutoMod Discord | можно оставить; правила Conductor живут в `data/automod.yml` и не управляются из `/admin` |
| Обзор безопасности | не обязателен |

### 7.4. Сообщество, витрина, онбординг

- **Server Discovery / витрина** — не включайте, если сервер не должен светиться в каталоге Discord.
- **Onboarding** Discord (каналы «пройди шаги») конфликтует с воронкой `#верификация`. На тестовом лучше выкл. На основном — либо выкл, либо не прячьте `#верификация` и `#правила` за онбордингом.
- **Community** (объявления, ветки) можно включить позже, на запуск бота не влияет.

### 7.5. Интеграции

**Настройки сервера → Интеграции**:

- Должен быть только нужный Conductor (основной или тестовый).
- DSMonitoring и Server Monitoring выгоните заранее: Conductor их не кикает, только показывает в `/diagnose`. Снимите их интеграции и каналы «бамп».
- Других конструкторов с теми же каналами не держите.

### 7.6. Приватность каналов до seed

Пока каркаса нет, достаточно чтобы роль бота видела сервер. После подключения права категорий выставит бот. Канал `#правила` создаёте пустым: текст пишете вы.

### 7.7. Владелец сервера

Сид выдаёт ранг «Специальный следящий» **владельцу сервера**, если этот ранг ещё никому не выдан. Владелец приложения и владелец сервера могут быть разными людьми.

## 8. Файл `.env`

В корне репозитория:

```powershell
Copy-Item .env.example .env
```

Пустая строка = «не задано». Токен и пароль базы пустыми оставлять нельзя.

### 8.1. Один процесс: переключаете режим

В одном `.env` указываются оба токена. `BOT_MODE` выбирает, какой токен и какой список серверов возьмёт процесс.

```
BOT_MODE=live
DISCORD_TOKEN=токен-основного-приложения
GUILD_IDS=id-общедоступного-сервера
TEST_DISCORD_TOKEN=токен-тестового-приложения
TEST_GUILD_IDS=id-тестового-сервера
OWNER_USER_IDS=
POSTGRES_PASSWORD=длинный-пароль-латиница-цифры
```

- `BOT_MODE=live` — процесс ходит в Discord как основной бот: `DISCORD_TOKEN` и `GUILD_IDS`.
- `BOT_MODE=test` или `beta` — тот же контейнер переключается на тестового: `TEST_DISCORD_TOKEN` и `TEST_GUILD_IDS`.

Чтобы сменить бота: поменяйте `BOT_MODE` и перезапустите (`.\stop.ps1`, затем `.\start.ps1`). Оба из одного файла одновременно не стартуют.

Запасные ключи, если списки пусты:

- live → `PUBLIC_GUILD_ID`;
- test/beta → `TEST_GUILD_ID`, иначе `GUILD_IDS` этого файла.

### 8.2. Оба онлайн сразу: второй файл

1. `Copy-Item .env .env.test`
2. В `.env.test`:
   - `BOT_MODE=test`
   - `DISCORD_TOKEN=` токен **тестового** приложения
   - `GUILD_IDS=` id тестового сервера
   - `TEST_DISCORD_TOKEN` можно не дублировать
3. Основной `.env` оставьте с `BOT_MODE=live` и токеном основного.

`.env` и `.env.test` в git не попадают.

### 8.3. Пароль Postgres

Для Docker обязателен `POSTGRES_PASSWORD`. Лучше латиница и цифры. Символы `@ : / # ? %` ломают URL, если собирать `DATABASE_URL` руками; Compose собирает URL сам.

## 9. Запуск процесса

Windows, Docker Desktop зелёный:

```powershell
.\start.ps1
```

Поднимаются postgres и контейнер `bot` из `.env`. Логи — в этой консоли. `Ctrl+C` закрывает только просмотр.

Пустой Ubuntu 24.04 — отдельная инструкция и скрипты: [deploy/ubuntu-24.04/README.md](../deploy/ubuntu-24.04/README.md).

```bash
sudo bash deploy/ubuntu-24.04/bootstrap.sh --ufw
./deploy/ubuntu-24.04/start.sh
```

Второй бот параллельно:

```powershell
docker compose --profile test up -d
docker compose logs -f bot-test
```

Нужен файл `.env.test`. Данные тестового контейнера — `./data-test`. База Postgres общая, строки разделены по `guild_id`.

Остановка всех копий: `.\stop.ps1`.

Стереть базу и все рабочие данные бота (снимки SQLite, дампы `backups/`, `data-test`, `.command-hash`, `.heartbeat`, `.create-lock.json`, `automod.yml`) и начать настройку с чистого листа:

```powershell
.\stop.ps1
.\.venv\Scripts\python.exe scripts\wipe_data.py
.\.venv\Scripts\python.exe scripts\wipe_data.py --yes
.\start.ps1
```

`.env` и эталоны `*.yml.example` остаются. Роли и каналы в Discord скрипт не удаляет. Если Discord подтвердил 429 на создание ролей или каналов, очистка базы бан не снимает. Предсказание библиотеки и квота бота в файл не пишутся.

В логе старта должны быть `preflight` с нужным `bot_mode` и списком `guild_ids`, затем `ready`. Если бот зашёл на чужой сервер — строка `leaving_foreign_guild` / `rejecting_guild`.

Без Docker (только разработка): свой venv, `BOT_MODE`, токен и `GUILD_IDS` в `.env`, свой `DATA_DIR` у тестового процесса.

## 10. Первые команды

Команды видны на сервере, который есть в списке **запущенного** процесса. Пишет владелец приложения (или id из `OWNER_USER_IDS`).

На **тестовом** сервере, когда запущен тестовый бот:

1. `/diagnose` → **Настройка**: интенты, права, позиция роли — без красного.
2. `/admin` → **Каркас** → **Собрать сервер**. Бот создаёт недостающее сам. Настоящий 429 Discord, предсказание библиотеки, общий лимит и квота бота — разные тексты; в файл уходит только подтверждённый 429 и не дольше часа. Не удаляйте объекты пачками и не чистите базу «чтобы начать заново».
3. Есть свои каналы? **Сопоставить существующие** до сборки. Имена чужих каналов бот не меняет.
4. `/admin` → **Каркас** → **Витрины** → **Отправить все недостающие**.
5. Правила в `#правила` пишет владелец сервера.
6. `/diagnose` → **Готовность**: должно быть «сервер готов к работе».

Параметр `with_old` у `/owner seed` — только если роли Old нужны сразу. Свои чаты общения — внутри категории «Сервер» после сборки.

Когда тестовый каркас вас устраивает, запустите основной процесс (`BOT_MODE=live`) и повторите сборку **на общедоступном** сервере тем же порядком. Не гоняйте seed основного бота на тестовом сервере.

`/owner emojis` — загрузка значков приложения, тоже останавливается при лимите на создание эмодзи. `/owner limits` — список блокировок создания и снятие записи бота.

## 12. После seed

Дальше — каркас, `/admin panel`, автомод, Old, живой сервер со старой репутацией.

### Пустой сервер за пять минут

1. Нужный бот приглашён, роль выше каркаса, процесс запущен.
2. `/admin` → **Каркас** → **Собрать сервер**. Есть свои каналы — сначала **Сопоставить существующие**.
3. Правила в `#правила`.
4. `/admin` → **Каркас** → **Витрины** → **Отправить все недостающие**.
5. Свои чаты в категории «Сервер».
6. `/diagnose` → **Готовность**: «сервер готов к работе».

Лист приёмки (матрица, сценарии A–C, границы) — [ACCEPTANCE.md](ACCEPTANCE.md).

### Что происходит после выдачи Специального

Пока ранг Специального никому не привязан, люди с галкой Discord «Администратор» видят команды бота — это запасной вход пустого сервера. Как только роль Специального привязана в `/admin` → Ранги, запасной вход закрывается. Дальше команды идут по ключам и рангам: Главный Следящий ведёт сервер, Специальный владеет необратимым (права, кадры, репутация, достижения, данные).

Если роль Специального удалят в Discord, бот снимет осиротевшую привязку и снова откроет запасной вход администраторам — сервер можно починить, а не потерять.

### Если доступ потерян

1. Владелец приложения Discord и id из `OWNER_USER_IDS` всегда проходят проверки рангов.
2. `/diagnose` → Настройка: «Вернуть умолчания прав» восстанавливает ключи из схемы, ранговые роли не трогает.
3. Страница `/admin` → Права: та же кнопка и выгрузка YAML.
4. Скрипт `scripts/verify_skeleton.py` покажет серверы, где привязка Специального уже пуста.

### Права и роль бота

Список `domain/permissions.py: REQUIRED_PERMISSIONS` — таблица в §6. Проверка: `/diagnose` → Настройка.

### `/owner seed`

Доступна владельцу бота на обслуживаемом сервере. Это каталог каркаса и запасной вход, не основной способ настройки.

- Каналы и роли каркаса создаёт `/admin` → **Каркас** → **Собрать сервер**.
- `/owner seed` по-прежнему умеет усыновлять уже существующие объекты по имени. Имена чужих каналов не меняются.
- Каналы общения команда не создаёт.
- Special выдаётся владельцу сервера, если ранг ещё свободен.
- Каталожных ботов бот не кикает.
- Пустая категория «Сервер» после подключения — норма.
- После игровых ролей выдайте им `view_channel` на каналы и войсы этих игр сами. В чужие каналы бот не лезет.
- Комнаты, тикеты и группы по-прежнему создают каналы по одному; предохранитель ограничивает частоту create/delete и останавливается после длинного 429.

Полная таблица каркаса — [FEATURES.md](FEATURES.md) §8.

### Настройка файлом

Файл удобнее панели, когда нужно перенести настройку с тестового сервера на основной, держать её в git или править много полей сразу.

1. `/owner export` — скачается `conductor-<id сервера>-<дата>.json`. Ответ эфемерный. В файле есть id сервера: не выкладывайте его публично.
2. Правите поля. Ключи с подчёркиванием — пояснения, бот их отбрасывает.
3. `/owner apply` с файлом. По умолчанию режим «проверить»: карточка плана (изменения, создание, ошибки, предупреждения).
4. Кнопка **Применить файл** — только у того же владельца. Режим «применить» сразу проходит, только если ошибок нет.

`null` снимает привязку. Каналы и роли Discord по файлу не удаляются. Неизвестный раздел не блокирует остальное: лишнее попадает в отчёт.

## Если бот молчит

1. `/diagnose` на этом сервере. Нет команды — вы не на сервере из списка **запущенного** процесса, или команды ещё не синхронизировались: перезапуск или `FORCE_SYNC=true` на один запуск.
2. В `.env` id этого сервера есть у текущего `BOT_MODE`. Основной не обслуживает тестовый сервер и наоборот. С чужого бот выходит сам.
3. Public Bot выкл не мешает вам приглашать со своего аккаунта; мешает посторонним.
4. Интенты Members и Message Content включены, процесс перезапущен после галок.
5. Роль бота выше ролей каркаса, в инвайте были `bot` и `applications.commands`.
6. В логе нет `leaving_foreign_guild` для нужного сервера и нет `В .env нет токена`.
